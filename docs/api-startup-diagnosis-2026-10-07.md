# noda-api 部署「健康等待 210s」诊断报告

- 日期：2026-10-07（依据 #661 现场 + 当日实测）
- 性质：**零改动诊断**——本报告未改任何配置、未重启任何容器
- 关联：`docs/superpowers/specs/2026-10-07-deploy-throughput-governance-design.md` SP3

## 结论（TL;DR）

**「点了批准后 API 迟迟不部署」的主因不是应用启动慢、不是健康判定慢，而是 docker 守护进程创建容器就花了 191 秒**；当时 r4s 正在与 #660 静态发版的快照轮转并行（weed 32 并发 COPY 压满磁盘/daemon），且系统 swap 已用 99.6%。应用本体从启动到全部监听就绪只要 **15 秒**，健康探针在监听就绪后 **9 秒**即通过（`/api/health` 是纯静态 JSON，不碰数据库）。

## 归因拆解

| 段 | 实测 | 归因 | 可优化性 |
|---|---|---|---|
| 镜像传输 | 39s | registry 增量已最优 | 无 |
| **docker create 停滞** | **191s** | daemon 在资源争抢（轮转 IO + swap 满载）下创建容器极慢 | **高（消除并发/清 swap 债）** |
| 应用启动→监听 | 15s | 迁移无瓶颈（31 个增量校验）；连接池/路由初始化快 | 无需 |
| 健康判定 | 9s | 静态端点 + 5s 探针间隔，已最优（dc2c2a8 的 30s→5s 修复方向正确但收益本来就小） | 无 |
| 蓝绿切流 | 84s | stop-timeout 30s 优雅退场 + 换名起停 | 低（缩 stop-timeout 有在途请求风险，已否决过） |

排除项：无 OOMKilled、RestartCount=0；健康检查配置（5s/10s/30s×3）合理；**此前假设的「迁移慢」「健康判定延迟」「容器限额 256MB 不够」（稳态实测仅 63-120MiB）均被证伪**。

## 立项建议（两条路径，供拍板）

### 路径 A：r4s 资源治理（推荐，预计 API Deploy Prod 8min→~3.5min）
1. **跨层部署串行化**：管线 queue gate 目前只按产品互斥；让 static 与 api 两条发布线互斥（或 Jenkins 关闭并行构建）。仅此一条即可消除 191s 争抢停滞。
2. **swap 债清偿与防复发**：958MB/1024MB 满载（10-05 事故同款模式）；按既有 SOP 停负载→清债，守卫 cron 已在场。
3. **weed 容器限额评估**：1.5GiB 限制下轮转期实测涨到 1.36GiB（2.1× 空闲值），余量偏紧；总内存 3.7GB 可考虑放宽至 2-2.5GiB（需连带评估 immich 等）。

### 路径 B：应用侧优化（不推荐先做）
启动 15s、健康 9s、健康端点零 DB——应用侧没有可摘的果子。唯一遗留选项是「jobs 容器不阻塞发布」（省 ~1-2min，语义变化：cron worker 可异步等健康），属旧议题。

## 附带发现（2026-10-07 实测）

- weed 在 64 并发服务端 sync 下内存 621MiB→1.36GiB（本轮轮转现场持续观测）；速率 ~44 obj/s 饱和，128 并发无增益（见 `docs/deploy-expectations.md` 压测数据）。
- r4s BusyBox `free` 的 available 列才是真实可用水位（free 列只有几十 MB 是 cache 计法）；`/tmp` 在 docker 容器间不共享且单文件 bind-mount 会被 docker 建成目录（已知怪癖的实锤复现）。
