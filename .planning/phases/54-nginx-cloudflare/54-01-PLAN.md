set $findclass_upstream noda-apps-green:3000;

set $auth_app_upstream noda-apps-green:3004;
set $admin_upstream noda-apps-green:3006;

### Server Block 结构（来自 `default.conf`）

```nginx
server {
    listen 80;
    server_name class.noda.co.nz;

    include /etc/nginx/snippets/upstream-findclass.conf;

        proxy_pass http://$findclass_upstream;
        include /etc/nginx/snippets/proxy-common.conf;
    }
}
```

### Task 2: 扩展 default.conf 添加 Forwarded Protocol 映射

**文件：** `config/nginx/conf.d/default.conf`

**动作：**
1. 在文件顶部的 `map $host $forwarded_proto` 块中添加 4 个 pre-prod 域名条目：
   - `pre.class.noda.co.nz "https";`
   - `pre.auth.noda.co.nz "https";`
   - `pre.noda.co.nz "https";`
   - `pre.admin.noda.co.nz "https";`
2. 在 `map $host $forwarded_port` 块中添加对应的端口映射：
   - `pre.class.noda.co.nz "443";`
   - `pre.auth.noda.co.nz "443";`
   - `pre.noda.co.nz "443";`
   - `pre.admin.noda.co.nz "443";`
3. 保持现有 prod 域名的 map 条目不变

**避免：** 不要删除或修改现有的 prod 域名 map 条件。

**为什么：** Pre-prod 域名需要正确的 `X-Forwarded-Proto` 和 `X-Forwarded-Port` 头（https 和 443），否则应用层会检测到错误的协议。

**验证：**
```bash

grep -c "pre\..*\.noda\.co\.nz.*https" config/nginx/conf.d/default.conf
# 预期输出：4

# default.conf 包含 4 个 pre-prod 域名的 forwarded_port 映射
grep -c "pre\..*\.noda\.co\.nz.*443" config/nginx/conf.d/default.conf
# 预期输出：4

# 现有 prod 域名映射未受影响
grep "class\.noda\.co\.nz.*https" config/nginx/conf.d/default.conf
# 预期输出：至少 1 行（prod 域名）
```

**完成标准：**
- `default.conf` 包含 4 个 pre-prod 域名的 `forwarded_proto` 映射（值 `"https"`）
- `default.conf` 包含 4 个 pre-prod 域名的 `forwarded_port` 映射（值 `"443"`）
- 现有 prod 域名的映射未受影响

### Task 3: 创建 Pre-Prod Server Blocks

**文件：** `config/nginx/conf.d/default.conf`

**动作：**
1. 在 `default.conf` 末尾（最后一个 `}` 之前）添加 4 个新的 server blocks：
   - `pre.class.noda.co.nz` → 类似 `class.noda.co.nz`，但使用 pre-prod upstream
   - `pre.auth.noda.co.nz` → 类似 `auth.noda.co.nz`，但 Auth App 使用 pre-prod upstream，Keycloak 使用共享 upstream
   - `pre.noda.co.nz` → 类似 `noda.co.nz`，但使用 pre-prod upstream
   - `pre.admin.noda.co.nz` → 类似 `admin.noda.co.nz`，但使用 pre-prod upstream
2. 每个 server block 必须使用 `include /etc/nginx/snippets/upstream-findclass-preprod.conf`（而非 prod upstream）
3. 每个 server block 的 `server_name` 必须是 pre-prod 域名（例如 `pre.class.noda.co.nz`）
4. 所有 location 规则、proxy 配置、安全头保持与 prod server block 一致
5. **特别注意 `pre.auth.noda.co.nz`：**
   - Auth App 的 location（`/`、`/login`、`/api/` 等）使用 `$auth_app_preprod_upstream`
   - Keycloak 的 location `location /`（兜底）使用 `$keycloak_upstream`（共享 prod 实例）

**避免：**
- 不要复制 prod 的 upstream 文件路径（必须改为 `upstream-findclass-preprod.conf`）
- 不要修改 prod 的 server blocks（只添加新的）
- 不要改变 location 匹配顺序（Auth App 的精确匹配和前缀匹配必须在 Keycloak 的兜底匹配之前）

**为什么：**
- Pre-prod 需要独立的 upstream 变量（避免蓝绿切换时修改 prod upstream）
- Keycloak 共享实例（无需 pre-prod 独立容器），但 Auth App 需要 pre-prod 版本
- Location 顺序错误会导致所有请求路由到 Keycloak（Auth App 无法访问）

**验证：**
```bash
# default.conf 包含 4 个 pre-prod server_name
grep -c "server_name.*pre\..*\.noda\.co\.nz" config/nginx/conf.d/default.conf
# 预期输出：4

# 所有 pre-prod server blocks 使用 pre-prod upstream
grep -A 2 "server_name.*pre\..*\.noda\.co\.nz" config/nginx/conf.d/default.conf | grep -c "upstream-findclass-preprod"
# 预期输出：4

# pre.auth.noda.co.nz 同时使用 pre-prod upstream 和 shared keycloak upstream
grep -A 50 "server_name pre.auth.noda.co.nz" config/nginx/conf.d/default.conf | grep -c "auth_app_preprod_upstream"
# 预期输出：> 0（Auth App 使用 pre-prod）

grep -A 50 "server_name pre.auth.noda.co.nz" config/nginx/conf.d/default.conf | grep "location /" | grep -c "keycloak_upstream"
# 预期输出：> 0（Keycloak 使用共享）
```

**完成标准：**
- `default.conf` 包含 4 个 pre-prod server blocks
- 所有 pre-prod server blocks 引用 `upstream-findclass-preprod.conf`
- `pre.auth.noda.co.nz` 的 Auth App 路由使用 `$auth_app_preprod_upstream`
- `pre.auth.noda.co.nz` 的 Keycloak 路由使用 `$keycloak_upstream`
- Prod server blocks 未受影响

### Task 4: 验证并重载 Nginx 配置

**动作：**
1. 检查 Nginx 配置语法：
   ```bash
   docker exec noda-infra-nginx nginx -t
   ```
2. 如果语法检查通过，重载 Nginx：
   ```bash
   docker exec noda-infra-nginx nginx -s reload
   ```
3. 验证 upstream 变量已加载：
   ```bash
   docker exec noda-infra-nginx cat /etc/nginx/snippets/upstream-findclass-preprod.conf
   ```
4. 验证 server blocks 已加载：
   ```bash
   docker exec noda-infra-nginx grep "pre\..*\.noda\.co\.nz" /etc/nginx/conf.d/default.conf
   ```

**避免：** 如果 `nginx -t` 失败，不要执行 `nginx -s reload`（会导致 Nginx 进程退出）。先修复语法错误，再重新验证。

**为什么：** 配置错误会导致 Nginx 无法启动，影响所有域名（包括 prod）。

**验证：**
```bash
# Nginx 进程运行中

# 预期输出：容器状态为 "Up"

# 预期输出：退出码 0

# server blocks 已生效
docker exec noda-infra-nginx nginx -T 2>/dev/null | grep -c "pre\..*\.noda\.co\.nz"
# 预期输出：>= 4
```

**完成标准：**
- `nginx -t` 返回 `syntax is ok` 和 `test is successful`
- `nginx -s reload` 执行成功（无错误输出）
- Nginx 容器仍在运行（未因配置错误退出）
- upstream 文件和 server blocks 已挂载到容器

## 威胁模型

### 信任边界

| 边界 | 描述 |
|------|------|
| 外部用户 → Cloudflare → Nginx | Pre-prod 域名流量与 prod 流量隔离（不同域名），但共享同一 Nginx 实例 |
| Nginx → Pre-prod 后端容器 | 当前无后端容器（Phase 55 创建），预期返回 502 |
| Nginx → Keycloak | `pre.auth.noda.co.nz` 的 Keycloak 路由共享 prod 实例 |

### STRIDE 威胁登记表

| 威胁 ID | 类别 | 组件 | 处置 | 缓解措施 |
|---------|------|------|------|----------|
| T-54-01 | 信息泄露 | Upstream 配置文件 | 接受 | upstream 变量名不包含敏感信息，容器名在 Docker 网络内可见 |
| T-54-02 | 篡改 | default.conf | 接受 | 配置文件在 Git 仓库版本控制，修改需要 commit review |
| T-54-03 | 拒绝服务 | Nginx 配置错误 | 缓解 | 执行 `nginx -t` 验证语法后才重载，避免配置错误导致 Nginx 退出 |
| T-54-04 | 权限提升 | Pre-prod 域名访问 prod 后端 | 缓解 | Pre-prod server blocks 使用独立的 upstream 变量（`_preprod_` 前缀），不会路由到 prod 容器 |
| T-54-05 | 跨站脚本（XSS） | Forwarded Protocol 头 | 缓解 | 添加 pre-prod 域名到 map 指令，确保 `X-Forwarded-Proto: https` 和 `X-Forwarded-Port: 443` |
