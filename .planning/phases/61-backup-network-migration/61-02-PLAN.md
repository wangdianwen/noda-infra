验证 Cloudflare Tunnel 在 r4s 上正常运行，确认 Docker 内部 DNS 解析正确。

**步骤 1.1 — 检查 cloudflared 进程状态：**
- 检查 supervisord 进程状态: `ssh root@r4s 'docker exec noda-ops supervisorctl status'`
- 预期输出: cron RUNNING, cloudflared RUNNING
- 如果 cloudflared 状态为 FATAL 或 BACKOFF，查看错误日志诊断

**步骤 1.2 — 检查 cloudflared 日志：**
- 查看错误日志最后 30 行: `ssh root@r4s 'docker exec noda-ops tail -30 /var/log/noda-backup/cloudflared-error.log'`
- 查看标准日志最后 20 行: `ssh root@r4s 'docker exec noda-ops tail -20 /var/log/noda-backup/cloudflared.log'`
- 关键检查点：
  - 日志中应包含 "Connection ... registered" 或类似成功连接消息
  - 不应出现 "DNS resolution failed" 或 "connection refused" 错误
  - 注意日志中显示的 service URL 是 `nginx:80` 还是 `noda-nginx:81`（per RESEARCH Pitfall 1）

**步骤 1.3 — 验证 Docker 内部 DNS 解析（per D-02）：**
从 noda-ops 容器内测试 DNS 解析到 Nginx：
- 测试服务名: `ssh root@r4s 'docker exec noda-ops sh -c "wget -qO- http://nginx:80/health 2>/dev/null || echo FAILED-nginx-80"'` — 如果 nginx:80 有 server block 响应，返回内容
- 测试服务名 81 端口: `ssh root@r4s 'docker exec noda-ops sh -c "wget -qO- http://nginx:81/health 2>/dev/null || echo FAILED-nginx-81"'` — prod server blocks 监听 81
- 测试容器名: `ssh root@r4s 'docker exec noda-ops sh -c "wget -qO- http://noda-infra-nginx:81/health 2>/dev/null || echo FAILED-noda-infra-nginx-81"'`
- 测试 config.yml 中的名称: `ssh root@r4s 'docker exec noda-ops sh -c "wget -qO- http://noda-nginx:81/health 2>/dev/null || echo FAILED-noda-nginx-81"'` — config.yml 使用 noda-nginx

**重要分析：** 根据日志和 DNS 测试结果，判断：
1. 如果 nginx:81 和 noda-infra-nginx:81 都返回成功 → Docker DNS 正常，prod 路由正常
2. 如果 noda-nginx:81 失败但 nginx:81 成功 → config.yml 中的名称需要更新（虽然 token 模式下不影响）
3. 如果全部失败 → Docker 网络 noda-network 配置有问题

**步骤 1.4 — 外部域名可达性验证（per NET-01）：**
- 从 Mac 验证生产域名: `curl -sf -o /dev/null -w "%{http_code}" https://class.noda.co.nz/api/health` — 预期返回 200
- 验证 auth 域名: `curl -sf -o /dev/null -w "%{http_code}" https://auth.noda.co.nz/` — 预期返回 200 或 302（重定向到登录）
- 如果外部验证失败但 cloudflared 进程正常，检查：
  - Cloudflare Dashboard 中 Tunnel 配置的 service URL 是否正确（应为 nginx:81 或 noda-infra-nginx:81）
  - Mac 上是否有旧 noda-ops 容器仍在运行 Tunnel（竞争连接）

**步骤 1.5 — 检查 Mac 上是否有 Tunnel 冲突（per RESEARCH Pitfall 6）：**
- 在 Mac 上检查: `docker ps -a --filter name=noda-ops --format "{{.Names}} {{.Status}}"`
- 如果 Mac noda-ops 仍在运行，记录为警告但不处理（Plan 03 统一处理）

- 如果端口映射不完整，检查 docker-compose.r4s.yml 是否正确应用（`-f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.r4s.yml`）

**步骤 2.3 — 验证端口 8443 (HTTPS pre-prod 内容):**
- 从 Mac 测试 pre-prod HTTPS: `curl -k https://<R4S_IP>:8443/api/health`
- 预期: HTTP 200，返回健康检查 JSON
- 注意: 需要使用 -k 跳过证书验证（自签名证书或 pre-prod 域名不匹配）

**步骤 2.4 — 验证 pre-prod 域名路由（per NET-03, D-10）：**

获取 r4s IP 后，配置本地 /etc/hosts（需要 sudo 权限）：

- 注意: 实际域名是 `*.noda.test`（不是 D-10 中的 `class.noda.dev`，per RESEARCH Pitfall 4）

验证各 pre-prod 域名通过 8443 端口访问：
- class.noda.test: `curl -k https://class.noda.test:8443/api/health` — 预期 200
- auth.noda.test: `curl -k -I https://auth.noda.test:8443/` — 预期 200 或 302
- www.noda.test: `curl -k -I https://www.noda.test:8443/` — 预期 200 或 302
- admin.noda.test: `curl -k -I https://admin.noda.test:8443/` — 预期 200 或 302

验证 pre-prod 域名通过 8080 端口访问（HTTP 重定向）：

- HTTPS 证书错误: 检查 Nginx SSL 配置，pre-prod 可能使用自签名证书
- 域名不匹配: 确认 Nginx server_name 配置中的域名与 /etc/hosts 一致
